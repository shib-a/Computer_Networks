## 1. Введение

FL/1 — прикладной протокол для организации федеративного обучения нейронных сетей. Протокол обеспечивает:

- координацию раундов обучения между сервером и множеством клиентов;
- передачу архитектуры модели и весов по сети;
- агрегацию локальных обновлений на сервере (алгоритм FedAvg);
- репликацию состояния сервера для отказоустойчивости (primary/backup).

### Участники

| Роль | Описание |
|------|----------|
| **Server** | Постоянно работающий процесс. Хранит глобальную модель, координирует раунды, агрегирует обновления. |
| **Client** | Краткоживущий процесс. Получает модель, обучает её на локальных данных, возвращает веса. |
| **Primary** | Активный сервер в HA-конфигурации. |
| **Backup** | Резервный сервер в HA-конфигурации. Хранит реплику состояния primary. |

## 2. Термины и обозначения

| Термин | Определение |
|--------|-------------|
| **task** | Сущность на сервере, представляющая одну задачу обучения: модель, счётчик раундов, накопленные обновления. |
| **round** | Один цикл: рассылка весов → локальное обучение → сбор обновлений → агрегация. |
| **arch_bytes** | Байтовый буфер с моделью, сериализованной через TorchScript (`torch.jit.save`). |
| **weights_bytes** | Байтовый буфер с `state_dict` модели, сериализованным через `torch.save`. |
| **state_dict** | Словарь `{имя_параметра → тензор}`, описывающий значения всех весов модели. |
| **FedAvg** | Federated Averaging — взвешенное среднее `state_dict` по числу обучающих примеров. |
| **quorum** | Минимальное количество клиентов, необходимое для агрегации раунда. |
| **snapshot** | Полный сериализуемый снимок состояния всех задач (используется для репликации). |

## 3. Транспортный уровень

### 3.1 Протокол транспортного уровня: TCP

FL/1 работает поверх TCP (RFC 793). Выбор TCP обусловлен:

- **Надёжность**: веса модели — бинарные данные объёмом от сотен КБ до ГБ. Потеря или переупорядочивание байт сделает десериализацию невозможной.
- **Упорядоченность**: pickle-десериализация требует, чтобы байты пришли в точном порядке.
- **Управление потоком**: сервер, не успевающий читать, автоматически притормаживает отправителя — без дополнительного кода.

### 3.2 Порты по умолчанию

| Назначение | Порт |
|-----------|------|
| Primary → Clients | 9000 |
| Backup → Clients (после промоции) | 9100 |
| Primary → Backup (репликация) | 10100 |

### 3.3 Жизненный цикл соединения

```
Client                          Server
  |                               |
  |──── TCP SYN ─────────────────>|
  |<─── TCP SYN-ACK ──────────────|
  |──── TCP ACK ─────────────────>|
  |                               |
  |    [FL/1 сообщения]           |
  |                               |
  |──── TCP FIN ─────────────────>|  (клиент завершает работу)
  |<─── TCP FIN-ACK ──────────────|
```

Одно TCP-соединение используется клиентом на протяжении всего участия в задаче (несколько раундов). Сервер не закрывает соединение первым, кроме случая отправки `DONE`.

## 4. Формат сообщения

### 4.1 Структура фрейма

TCP — потоковый протокол без понятия о границах сообщений. FL/1 использует явное фреймирование с полем длины:

```
 0        1        2        3        4        5        6        7        8
 0        8        6        4        2        0        8        6        4
 ┌────────┬────────┬────────┬────────┬────────┬────────┬────────┬────────┬────────┐
 │   Magic[0]     │   Magic[1]      │   Magic[2]      │   Magic[3]      │ MsgType│
 ├────────┴────────┴────────┴────────┴────────┴────────┴────────┴────────┼────────┤
 │                       PayloadLen (4 байта, big-endian)                │       │
 └───────────────────────────────────────────────────────────────────────┘
                              9 байт заголовка
 ┌─────────────────────────────────────────────────────────────────────────────────┐
 │                      Payload (PayloadLen байт)                                  │
 └─────────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 Поля заголовка

| Поле | Смещение | Размер | Тип | Описание |
|------|---------|--------|-----|----------|
| `Magic` | 0 | 4 байта | `bytes` | Идентификатор протокола: `0xFE 0xDE 0x00 0x01` |
| `MsgType` | 4 | 1 байт | `uint8` | Тип сообщения (см. раздел 5) |
| `PayloadLen` | 5 | 4 байта | `uint32 BE` | Длина payload в байтах |

Итого заголовок: **9 байт**.

### 4.3 Magic bytes

Значение `0xFEDE0001` выбрано как мнемоника **FEDE**rated learning, version **1**. Magic позволяет отклонить случайные подключения от посторонних клиентов (HTTP-сканеры, мониторинг и пр.) ещё до обработки payload.

Сервер **обязан** проверить Magic в каждом принятом сообщении. При несовпадении соединение закрывается немедленно.

### 4.4 Payload

Payload — это объект, сериализованный через Python `pickle` (protocol 4). Конкретная структура зависит от `MsgType` и описана в разделе 5.

Получатель **обязан** прочитать ровно `PayloadLen` байт. Неполный payload означает преждевременное закрытие соединения; в этом случае соединение считается разорванным.

### 4.5 Byte order

Все многобайтные числовые поля в заголовке передаются в **сетевом порядке байт (big-endian)**, согласно соглашению IETF.

### 4.6 Кодирование фрейма

```python
# Python: struct.pack('!4sBI', MAGIC, msg_type, len(payload))
# !   — network byte order (big-endian)
# 4s  — 4-byte string  → Magic
# B   — unsigned char  → MsgType (1 байт)
# I   — unsigned int   → PayloadLen (4 байта)
```

## 5. Типы сообщений

### 5.1 Сводная таблица

| Код | Имя | Направление | Описание |
|-----|-----|-------------|----------|
| `0x01` | `JOIN` | Client → Server | Присоединиться к задаче или получить список задач |
| `0x02` | `SUBMIT` | Client → Server | Отправить обновлённые веса |
| `0x03` | `STATUS` | Client → Server | Опросить статус раунда |
| `0x10` | `TASK_INFO` | Server → Client | Информация о задаче (arch + weights) |
| `0x11` | `WEIGHTS` | Server → Client | Новые глобальные веса после агрегации |
| `0x12` | `PENDING` | Server → Client | Раунд ещё не завершён |
| `0x13` | `DONE` | Server → Client | Обучение завершено |
| `0x20` | `HEARTBEAT` | Primary → Backup | Подтверждение активности primary |
| `0x21` | `REPL_STATE` | Primary → Backup | Полный снимок состояния |
| `0xF0` | `ACK` | Server → Client | Подтверждение приёма (ожидаем quorum) |
| `0xFF` | `ERROR` | Server → Client | Ошибка |

---

### 5.2 JOIN (`0x01`)

**Направление**: Client → Server

**Назначение**: присоединиться к задаче обучения. Если `task_id` равен `null`/`None`, сервер возвращает список задач вместо присоединения.

**Payload**:

```
{
    "task_id": str | null
}
```

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `task_id` | `str` или `null` | да | Идентификатор задачи; `null` → запрос списка |

**Возможные ответы**: `TASK_INFO`, `DONE`, `ERROR`

---

### 5.3 SUBMIT (`0x02`)

**Направление**: Client → Server

**Назначение**: отправить веса локально обученной модели.

**Payload**:

```
{
    "task_id":      str,
    "round_num":    int,
    "weights_bytes": bytes,
    "num_samples":  int
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `task_id` | `str` | Идентификатор задачи |
| `round_num` | `int` | Номер раунда, в котором получены веса (защита от рассинхронизации) |
| `weights_bytes` | `bytes` | `torch.save(state_dict)` — сериализованные обновлённые веса |
| `num_samples` | `int` | Количество обучающих примеров (используется для взвешивания в FedAvg) |

Если `round_num` не совпадает с текущим раундом задачи на сервере, обновление игнорируется, возвращается `ERROR`.

**Возможные ответы**: `WEIGHTS`, `ACK`, `DONE`, `ERROR`

---

### 5.4 STATUS (`0x03`)

**Направление**: Client → Server

**Назначение**: опросить, завершился ли указанный раунд. Используется клиентом в polling-цикле после получения `ACK`.

**Payload**:

```
{
    "task_id":   str,
    "round_num": int
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `task_id` | `str` | Идентификатор задачи |
| `round_num` | `int` | Номер раунда, который клиент ждёт завершения |

Логика ответа сервера:
- `server_round > round_num` → раунд завершён → `WEIGHTS`
- `server_round == round_num` и `is_done == False` → ещё ждём → `PENDING`
- `is_done == True` → `DONE`

**Возможные ответы**: `WEIGHTS`, `PENDING`, `DONE`

---

### 5.5 TASK_INFO (`0x10`)

**Направление**: Server → Client

**Назначение**: ответ на `JOIN`. Два варианта payload:

**Вариант A** — `task_id` был `null`, клиент запросил список:

```
{
    "tasks": [
        {
            "task_id":      str,
            "current_round": int,
            "max_rounds":   int,
            "min_clients":  int,
            "is_done":      bool
        },
        ...
    ]
}
```

**Вариант B** — клиент присоединился к конкретной задаче:

```
{
    "task_id":       str,
    "current_round": int,
    "max_rounds":    int,
    "arch_bytes":    bytes,
    "weights_bytes": bytes
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `arch_bytes` | `bytes` | `torch.jit.save(scripted_model)` — TorchScript-сериализованная архитектура модели |
| `weights_bytes` | `bytes` | `torch.save(state_dict)` — текущие глобальные веса |

`arch_bytes` содержит архитектуру модели в формате TorchScript IR. Клиент загружает её через `torch.jit.load()` без необходимости импортировать класс модели (Python или иной).

`weights_bytes` всегда содержит актуальные агрегированные веса на момент JOIN. Клиент вызывает `model.load_state_dict(torch.load(weights_bytes))` перед локальным обучением.

---

### 5.6 WEIGHTS (`0x11`)

**Направление**: Server → Client

**Назначение**: уведомление об успешной агрегации раунда. Содержит новые глобальные веса.

**Payload**:

```
{
    "task_id":       str,
    "round_num":     int,
    "weights_bytes": bytes
}
```

| Поле | Тип | Описание |
|------|-----|----------|
| `round_num` | `int` | Номер нового (только что начавшегося) раунда |
| `weights_bytes` | `bytes` | Новые глобальные веса после FedAvg |

Клиент может использовать `weights_bytes` напрямую для следующего раунда (без повторного JOIN), однако рекомендуется использовать JOIN для подтверждения актуальности состояния.

---

### 5.7 PENDING (`0x12`)

**Направление**: Server → Client

**Назначение**: ответ на `STATUS` — раунд ещё не завершён, quorum не набран.

**Payload**:

```
{
    "task_id":       str,
    "current_round": int
}
```

Клиент должен повторить `STATUS` через интервал (рекомендуется 2 секунды).

---

### 5.8 DONE (`0x13`)

**Направление**: Server → Client

**Назначение**: все раунды задачи завершены. После отправки этого сообщения сервер закрывает соединение со своей стороны.

**Payload**:

```
{
    "task_id":          str,
    "rounds_completed": int,
    "weights_bytes":    bytes
}
```

`weights_bytes` — финальные глобальные веса обученной модели.

---

### 5.9 ACK (`0xF0`)

**Направление**: Server → Client

**Назначение**: ответ на `SUBMIT` — веса приняты, но quorum ещё не набран. Клиент должен перейти к polling через `STATUS`.

**Payload**:

```
{
    "task_id": str,
    "message": str
}
```

---

### 5.10 ERROR (`0xFF`)

**Направление**: Server → Client

**Назначение**: сигнализирует об ошибке. Соединение остаётся открытым (клиент может повторить запрос).

**Payload**:

```
{
    "error": str
}
```

Типичные причины:
- `"unknown task 'xyz'"` — указанный `task_id` не существует
- `"send JOIN first"` — клиент отправил `SUBMIT` до `JOIN`
- `"wrong round: expected N, got M"` — клиент отправил веса для устаревшего раунда

---

### 5.11 HEARTBEAT (`0x20`)

**Направление**: Primary → Backup (по каналу репликации)

**Назначение**: подтверждение активности primary. Отправляется каждые 5 секунд при отсутствии других сообщений.

**Payload**:

```
{
    "ts": float
}
```

`ts` — Unix timestamp отправки (секунды с epoch).

---

### 5.12 REPL_STATE (`0x21`)

**Направление**: Primary → Backup (по каналу репликации)

**Назначение**: полный снимок состояния всех задач. Отправляется сразу при установлении реплика-соединения и после каждой агрегации.

**Payload**:

```
{
    "snapshot": {
        "<task_id>": {
            "task_id":                str,
            "arch_bytes":             bytes,
            "weights_bytes":          bytes,
            "current_round":          int,
            "max_rounds":             int,
            "min_clients_per_round":  int,
            "is_done":                bool
        },
        ...
    }
}
```

Pending-обновления текущего раунда не включаются в снимок. При failover незавершённый раунд начинается заново.

## 6. Диаграммы взаимодействия

### 6.1 Получение списка задач

```
Client                          Server
  │                               │
  │──── JOIN {task_id: null} ────>│
  │<─── TASK_INFO {tasks: [...]} ─│
  │                               │
  │  (клиент выбирает task_id и   │
  │   переподключается)           │
```

### 6.2 Нормальный раунд (клиент завершает quorum)

```
Client A                        Server                       Client B
  │                               │                              │
  │──── JOIN {task_id} ──────────>│                              │
  │<─── TASK_INFO {arch, w_t} ────│                              │
  │                               │                              │
  │ [train on D_A, E epochs]      │──── TASK_INFO {arch,w_t} ──>│
  │                               │<─── JOIN {task_id} ──────────│
  │                               │                              │
  │──── SUBMIT {w_A, n_A} ───────>│                              │
  │<─── ACK ──────────────────────│ [train on D_B, E epochs]    │
  │                               │<─── SUBMIT {w_B, n_B} ───────│
  │                               │                              │
  │                               │ FedAvg(w_A,w_B) → w_{t+1}  │
  │                               │──── WEIGHTS {w_{t+1}} ──────>│
  │──── STATUS {round_num: t} ───>│                              │
  │<─── WEIGHTS {round: t+1} ─────│                              │
```

### 6.3 Polling при незавершённом raунде

```
Client A        Server                   Client B
  │               │                          │
  │── SUBMIT ────>│                          │
  │<── ACK ───────│ (count 1/2)              │
  │               │                          │
  │── STATUS ────>│ (раунд ещё не готов)     │
  │<── PENDING ───│                          │
  │ [sleep 2s]    │                          │
  │── STATUS ────>│  ── SUBMIT ─────────────>│
  │               │  FedAvg → w_{t+1}        │
  │               │── WEIGHTS ──────────────>│
  │<── WEIGHTS ───│ (round_num > polled)      │
```

### 6.4 Завершение обучения

```
Client                          Server
  │                               │
  │──── JOIN {task_id} ──────────>│ (is_done == True)
  │<─── DONE {weights_bytes} ─────│
  │                               │
  │ [закрыть соединение]          │ [закрыть соединение]
```

### 6.5 Репликация Primary → Backup

```
Primary                        Backup
  │                               │
  │ [соединяется к :10100]        │
  │──── REPL_STATE {snapshot} ───>│ restore_snapshot()
  │                               │
  │ [каждые 5 сек]                │
  │──── HEARTBEAT {ts} ──────────>│ _last_contact = now()
  │                               │
  │ [после агрегации раунда]      │
  │──── REPL_STATE {snapshot} ───>│ restore_snapshot()
  │                               │
```

### 6.6 Failover: отказ Primary

```
Primary                        Backup (watchdog)           Client
  │                               │                           │
  │──── HEARTBEAT ───────────────>│ _last_contact = T         │
  │ *** CRASH ***                 │                           │
  │                               │ elapsed > 15s             │
  │                               │ → PROMOTE                 │
  │                               │ FLServer.start(:9100)     │
  │                               │                           │
  │                               │<── JOIN {task_id} ────────│ (retry)
  │                               │─── TASK_INFO ────────────>│
```

## 7. Конечные автоматы

### 7.1 Клиент

```
       ┌─────────────────────────────────────────────────────────┐
       │                                                         │
    START                                                        │
       │                                                         │
       ▼                                                         │
  ┌─────────┐  JOIN(null)  ┌──────────┐                         │
  │CONNECTED│─────────────>│LIST_TASKS│── показать список        │
  └─────────┘              └──────────┘   и выйти               │
       │                                                         │
       │ JOIN(task_id)                                           │
       ▼                                                         │
  ┌──────────┐             ┌──────────┐                         │
  │ TRAINING │─── SUBMIT ─>│ WAITING  │                         │
  └──────────┘             └──────────┘                         │
       ▲                        │                               │
       │                   ACK  │ WEIGHTS / PENDING             │
       │                   ─────┘                               │
       │  WEIGHTS (round завершён)                              │
       └──────────────────────────────────────────────────────  │
       │                                                         │
       │  DONE                                                   │
       ▼                                                         │
   ┌───────┐                                                     │
   │ EXIT  │─────────────────────────────────────────────────────┘
   └───────┘
```

### 7.2 Сервер (задача)

```
    CREATE_TASK
         │
         ▼
   ┌──────────┐
   │ WAITING  │  (ждём клиентов, current_round=0)
   └──────────┘
         │
         │  submit_update(): count < quorum
         │  (продолжаем ждать)
         │
         │  submit_update(): count >= quorum
         ▼
   ┌──────────────┐
   │ AGGREGATING  │  (FedAvg, обновление весов, round++)
   └──────────────┘
         │
         │ current_round < max_rounds
         ▼
   ┌──────────┐
   │ WAITING  │  (следующий раунд)
   └──────────┘

         │ current_round >= max_rounds
         ▼
   ┌──────────┐
   │   DONE   │  (is_done = True, все JOIN → DONE)
   └──────────┘
```

## 8. Протокол репликации

### 8.1 Топология

```
Primary (:9000)  ──────[FL/1 клиентский]──────  Client(s)
    │
    │ TCP соединение → Backup:10100
    │ (инициируется Primary)
    ▼
Backup (:10100, :9100)
```

Репликационный канал — отдельное TCP-соединение, не связанное с клиентскими соединениями. Primary является активной стороной (connect), Backup пассивной (listen).

### 8.2 Установка репликационного соединения

```
Primary                         Backup (:10100)
  │                               │
  │──── TCP connect ─────────────>│
  │──── REPL_STATE ──────────────>│  начальный снимок
  │                               │
  │ [далее — heartbeat loop]      │
```

Если соединение разрывается (backup перезагрузился, сеть), primary автоматически переподключается через 5 секунд и заново отправляет снимок.

### 8.3 Таймеры

| Параметр | Значение | Описание |
|----------|---------|----------|
| `HEARTBEAT_INTERVAL` | 5 с | Период отправки HEARTBEAT при отсутствии изменений |
| `HEARTBEAT_TIMEOUT` | 15 с | Задержка без контакта → backup промотируется |

Условие промоции: `now() - last_contact > HEARTBEAT_TIMEOUT`

### 8.4 Гарантии репликации

- **Репликация триггеруется событием**: после каждой агрегации `notify_state_changed()` устанавливает `threading.Event`. Если изменение произошло во время отправки предыдущего снимка — следующий снимок отправится немедленно без heartbeat.
- **At-most-once репликация pending-обновлений**: pending-обновления текущего раунда не реплицируются. При failover в середине раунда этот раунд начинается заново.
- **Без split-brain**: backup не обслуживает клиентов до промоции. После промоции backup начинает с актуального состояния; старый primary (если восстановится) не будет иметь клиентов — у него уже нет слушателей.

### 8.5 Восстановление снимка

При получении `REPL_STATE`:

1. Для каждой задачи в снимке:
   - Если задача не существует → создать через `from_snapshot()` (загружает модель из `arch_bytes` через `torch.jit.load`, применяет веса из `weights_bytes`)
   - Если задача существует → обновить `current_round`, `is_done`, `weights_bytes`, вызвать `model.load_state_dict()`
2. Ответ не отправляется (протокол репликации — однонаправленный push).

## 9. Обработка ошибок

### 9.1 Ошибки на уровне фрейма

| Ситуация | Действие |
|----------|----------|
| Magic не совпадает | Закрыть соединение немедленно |
| EOF до конца заголовка | `ConnectionError` — соединение разорвано |
| EOF до конца payload | `ConnectionError` — соединение разорвано |
| Неизвестный `MsgType` | Отправить `ERROR`, продолжить работу |

### 9.2 Ошибки на уровне приложения

| Ситуация | Ответ | Описание |
|----------|-------|----------|
| `JOIN` с несуществующим `task_id` | `ERROR` | Соединение остаётся открытым |
| `SUBMIT` до `JOIN` | `ERROR` | Требуется сначала JOIN |
| `SUBMIT` с неверным `round_num` | `ERROR` | Сервер игнорирует устаревшие обновления |
| `STATUS` до `JOIN` | `ERROR` | Требуется сначала JOIN |
| Pickle-ошибка при десериализации | Закрыть соединение | Данные повреждены |

### 9.3 Таймаут соединения

Сервер устанавливает `SO_TIMEOUT = 600 сек` на каждое клиентское соединение. Если за 10 минут не поступило ни одного сообщения — соединение закрывается.
